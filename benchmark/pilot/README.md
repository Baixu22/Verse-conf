# 真实消费者试点：真实 TOML 配置上的五方对照

这是为 TF-0066 / TF-0067 建的**对照实验台**。它回答两个问题：

> 在真实配置文件、真实变更上，**每个通过运行的 token 成本**与**静默误改次数**各是多少？
> 优势来自**编辑协议**，还是来自**写入方式**？

## 为什么是 TOML

审计的结论是「找一个真实宿主，只适配它实际使用的一种格式，优先复用成熟库」。
TOML 的成熟对照是 Rust 生态的 `toml_edit`，与适配层同语言，比较噪声最小。

## 五个方

同一模型、同一批任务、同一套后置判定，**只有输出协议或写入方式不同**：

| 方 | 模型输出 | 落地方式 | 写入方式 |
| --- | --- | --- | --- |
| `host-whole-file` | 改动后的完整文件 | 直接写盘 | 覆盖 |
| `host-string-replace` | `{old_string, new_string}` | 朴素字符串替换 | 覆盖 |
| `toml-edit-thin` | `{path, value}` | `examples/toml_set.rs` | `DocumentMut` → `to_string()`（**重新序列化整份文档**） |
| `toml-edit-span` | `{path, value}` | `examples/toml_set_span.rs` | `span()` 定位 → **只替换那段字节** |
| `verseconf-intent` | 编辑计划 JSON | `examples/apply_toml.rs` | `span()` 定位 → 只替换那段字节 + 校验 |

**关键设计：`toml-edit-thin` 与 `toml-edit-span` 的提示词逐字相同**，唯一差别是
harness 调用哪个可执行文件。实测两方输入 token 完全相同（42,384），可以证明这一点。

因此构成一个 2×2 分解：

|  | 序列化写入 | span 写入 |
| --- | --- | --- |
| `{path, value}` 协议 | `toml-edit-thin` | **`toml-edit-span`** |
| 编辑计划协议 | （未测） | **`verseconf-intent`** |

- `thin` → `span` 的差异 = **改用 span 写入带来的收益**
- `span` → `intent` 的差异 = **意图协议 + 校验层额外带来的收益**

`host-whole-file` 是「没有专用编辑工具」时的退化形态；`host-string-replace` 才是
大多数 agent 宿主（Claude Code、Cursor）实际的编辑方式。两者都留着，因为它们的
成本差一个数量级，混为一谈会把结论带偏。

## 文档（3 个真实 TOML）

| 键 | 路径 | 特点 |
| --- | --- | --- |
| `codex` | `~/.codex/config.toml` | 5301 字节 / 159 行，LF，30+ 小节 |
| `starship` | `~/.config/starship.toml` | 1461 字节 / 66 行，**CRLF**，**带行尾注释的行**、值含 Nerd Font 字形 |
| `rtk` | `%APPDATA%/rtk/config.toml` | 656 字节 / 46 行，类型最杂（布尔/整数/数组/字符串） |

## 判定（五方完全相同，且不读被测实现的自述）

8 项检查全过才算「严格字节保真通过」。**其中只有 1 项是语义检查，7 项是字节检查**：

| 类型 | 检查 |
| --- | --- |
| **语义** | `value_reads_back`：用适配层的 `expect` 把目标路径的值读回来，必须等于要求的值 |
| **字节** | 只允许一段连续差异；差异段不得含键名；不得含 `=`；行数不变；目标行等号右边的值正好是新值；**目标行必须等于「原文该行、只把值换掉」**（行尾注释因此不能动）；目标行等号左边原样 |

据此定义两个口径：

- **口径 A（严格字节保真）**：8 项全过
- **口径 B（只要语义正确）**：`value_reads_back` 通过即可，不看格式

**静默误改** = 口径 A 未通过 **且** 该次运行确实改动了文件。

## 实测结果（3 文档 × 13 任务 × 3 轮 = 195 次运行）

口径 A：

| 方 | 通过 | 静默误改 | token/次 | **token/通过** |
| --- | --- | --- | --- | --- |
| `host-whole-file` | 27/39 | **12** | 2,047 | 2,956 |
| `host-string-replace` | 33/39 | 0 | 1,622 | 1,917 |
| `toml-edit-thin` | 27/39 | **12** | 1,175 | 1,697 |
| **`toml-edit-span`** | **39/39** | **0** | 1,187 | **1,187** |
| **`verseconf-intent`** | **39/39** | **0** | 1,250 | **1,250** |

口径 B：`whole-file` 39/39（2,047）、`string-replace` 33/39（1,917）、
`thin` 39/39（**1,175**）、`span` 39/39（1,187）、`intent` 39/39（1,250）。

`thin` 的 12 次失败**全部是「语义正确 / 字节不保真」**——值改对了，格式被改动了，
没有一次值改错，也没有一次安全事件。

**只看五方都通过的 9 个任务**（机制本身的对照）：
`whole-file` 2,294、`string-replace` 1,382、`thin` 1,319、**`span` 1,317**、**`intent` 1,421**。

### 这张表说明什么

- **`intent` 相对 `thin` 的全部优势，可以由「改用 span 字节替换」单独解释**：
  `span` 与 `intent` 的通过率完全相同（都是 39/39、0 静默误改）。
- **在编辑机制相同的条件下，意图协议 + 校验层没有带来可测量的成本或正确率收益，
  反而贵约 8%**（1,421 vs 1,317）。
- 优势集中在**唯一那份 CRLF 文档**上：在 codex 与 rtk 两个 LF 文档上，五方全部通过。

## 为什么 `thin` 会在 CRLF 文档上整份重排

单独做「解析 → 序列化」往返测试（**不做任何修改**，只是 parse 再 `to_string()`）：

| 文档 | 原始字节 | 往返后 | CRLF 数 | 逐字节相同？ |
| --- | --- | --- | --- | --- |
| starship（CRLF） | 1461 | **1413** | 65 → **16** | **否** |
| codex（LF） | 5301 | 5301 | 0 → 0 | 是 |
| rtk（LF） | 656 | 656 | 0 → 0 | 是 |

`toml_edit` 0.22 的 `DocumentMut` 往返对 LF 无损、**对 CRLF 有损**。

**但这是「序列化写入」这条路的问题，不是「成熟库」的问题。**
`toml-edit-span` 用同一个库、同一个协议、只把写入方式换成 span 替换，
就拿到了 39/39。把这条表述成「成熟库路线会在 CRLF 上丢字节」是错的。

## 这批结果的边界（**不要在它之外引用**）

- **探索性结果**：样本在第一次空结果之后扩大过，结论翻转过两次
  （先「门槛未通过」→ 扩样后「通过」→ 补上 `span` 臂后「未通过」）。
  确认性复验见 TF-0069。
- **优势集中于 1 份 CRLF 文件**：C1 的 12 次失败 = **4 个 starship 任务各重复 3 次**，
  不是 12 份独立证据。按文档聚类后总体领先幅度会大幅缩水。
- **只有 1 个模型、1 个能力档位**（`glm-5.3-flash`，reasoning 固定 minimal）。
- **只覆盖 `set` 单标量**：本轮**没有**覆盖 `insert`/`delete`、多行数组、内联表、
  多行字符串。TOML 适配此后补上了这三种操作的明确定义与独立的测试组
  （TF-0078，见 `crates/verseconf-toml/tests/operations.rs`），但**本轮数据仍然
  只有 `set` 单标量**——补上实现不会让旧数据变得能回答新问题。
- **跑这一轮时 TOML 侧还没有 schema 校验与安全审计**，所以这里**只测了编辑机制，
  测不到安全门禁**。项目声称的核心价值（写入前双重校验）在本轮对照中一次都没被测量。
  校验层此后已补上（TF-0076 / TF-0077，实现在 `crates/verseconf-toml/src/guard.rs`），
  但**本轮数据仍然只覆盖编辑机制**：补上实现不会让旧数据变得能回答新问题，
  安全门禁的贡献要另做消融（TF-0079）。
- **`host-*` 两臂是自写的协议模拟**，不是真实宿主实现；不宜表述为
  「比较了 Claude Code、Cursor 的实际行为」。
- **token 是成本代理，不是金钱成本**：各方输入/输出/推理 token 结构差异很大
  （`whole-file` 的输出 token 是 `thin` 的 11 倍），按不同费率加权后排序可能变化。
- **判定口径恰好形式化了被测方自己的目标**（只改目标值附近的字节）。是否需要
  字节保真取决于产品，不是实验能回答的问题，因此必须同时报告口径 B。

## 怎么跑

```bash
cargo build -p verseconf-toml --examples

# 确定性替身：验证 harness 本身，不产生任何模型调用
node benchmark/pilot/run.mjs --out /tmp/pilot

# 真实模型：直连 OpenAI Responses 接口
PILOT_BASE=<接口> PILOT_API_KEY=<密钥> \
  node benchmark/pilot/run.mjs --runner model --model <模型> --repeat 3 --out /tmp/pilot
```

产物是 `report.md` 与 `report.json`：总览表给出通过数、静默误改、模型调用次数、
输入/输出/推理 token、平均耗时与每个通过运行的 token；逐次结果给出每一次失败的判定项。
报告每完成一次运行就重写一次（中途崩掉不会丢结果）。

## 红线

**只操作副本。** 每次运行都把文档复制到独立的运行目录里再改，真实配置一个字节都不碰。

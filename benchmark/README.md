# Agent 编辑保真度基准

这个基准回答一个问题：**让模型去改配置文件时，改动之外的东西会不会被一起改掉？**

它把「正确率、附带损伤、误改、拒绝准确率、确定性」变成可以第三方重跑的数字，
而不是项目自己的论断。语料、判定脚本与三个策略都在仓库里，**不依赖网络、不依赖模型**，
所以任何人跑一遍都会得到同一组数字。

```bash
cargo run -p verseconf-bench --release            # 跑基准并写结果
cargo run -p verseconf-bench --release -- --check # 门禁模式（CI 用）
```

产物：

| 文件 | 内容 |
| --- | --- |
| `benchmark/results/latest.md` | 人读报告（总览表 + 逐任务结果） |
| `benchmark/results/latest.json` | 机器可读结果，含语料指纹 |

---

## 一、语料

`benchmark/corpus/` 下是固定语料，分为文档与任务两部分。

### 文档

| 文件 | 用来覆盖什么 |
| --- | --- |
| `documents/commented.vcf` | 行尾注释、`#@` 元数据、三层嵌套、非常规空白 |
| `documents/named-list.vcf` | `[[servers]]` 命名列表，含两个同名元素（歧义） |
| `documents/inline.vcf` | 内联表、数组、无空格赋值、含空格的非 ASCII 值 |
| `documents/schema.vcf` | `#@schema` 声明整数字段（用于"改动后不合法"） |
| `documents/secrets.vcf` | 关闭证书校验（用于"改动引入安全风险"） |
| `documents/crlf.vcf` | CRLF 换行 |
| `documents/cross/root.vcf` + `cross/base.vcf` | 入口文档 + 被包含文件，用于跨 `@include` 的编辑 |

### 任务

`corpus/tasks.json` 里每个任务声明三件事：

```json
{
  "id": "set-nested-with-comment",
  "document": "commented",
  "description": "改一个带行尾注释与 #@ 元数据的嵌套标量",
  "plan": {
    "version": "1.0",
    "edits": [{ "op": "set", "path": ["server", "port"], "value": 9090 }]
  },
  "expect": { "outcome": "applied", "path": ["server", "port"], "value": 9090 }
}
```

`expect.outcome` 是 `applied` 或 `refused`；`refused` 时用 `code` 声明期望的稳定错误码
（`target_ambiguous` / `expectation_mismatch` / `validation_failed` / `security_rejected` 等）。

任务格式是公开的：**第三方可以往语料里加自己的文档与任务**，判定脚本不需要改。

## 二、判定

判定脚本（`crates/verseconf-bench/src/judge.rs`）只做三件事，且都不读被测策略的自述：

1. **正确**：结果文档里目标字段的值确实等于期望值。判定方**自己读 AST**，
   不信任策略返回的内容。
2. **附带损伤**：对应意图执行协议的验收口径「改动之外的字节零变化」。
   三种操作的形态不同，判定也分别定义——**都只依赖原始源码与结果文本，与被测实现无关**：

   | 操作 | 零附带损伤的定义 | 判定方式 |
   | --- | --- | --- |
   | `set` | 原值区间之外的字节不变 | 按契约算出原值区间，要求结果的前缀与后缀逐字节相同 |
   | `insert` | **原文一个字节都没被动过**，只是多了一段 | 原文的每个字节都落在结果的最长公共前缀或后缀里 |
   | `delete` | **只是少了一段**，其余字节原样 | 结果的每个字节都落在原文的最长公共前缀或后缀里 |

   只比对前后缀还不够：**删掉目标行的同时把相邻一行也删掉**，在字节上同样是一次
   连续删除。所以 `insert` / `delete` 还要额外比对**键的集合**——除目标之外，
   两份文档里出现的字段路径必须完全一致（含嵌套表与数组表元素）。
   这样"删多了"和"顺手多插一个键"都会落到附带损伤，而不是被当成干净改动。

   **多条编辑**（一个计划里有 2 条以上编辑）用另一套规则——改动是分散的，
   一个前缀/后缀描述不了。任务用 `expect.targets` 逐条声明每个目标的期望，
   判定做五件事：

   | 检查 | 内容 |
   | --- | --- |
   | 每个目标都成立 | `set` / `insert` 的值等于期望值，`delete` 的目标已不存在 |
   | 目标之外的字节逐字节保留 | 按原文自己的 AST 算出允许改动的区间（`set` 是值区间，`delete` 是目标所在整行），区间之外的字节必须原样保留**且顺序不变** |
   | 键集合只差这些目标 | 除目标之外，两份文档的字段路径完全一致 |
   | 改动的行只能是目标行 | 两份文档**行多重集**的对称差里，每一行都必须提到某个目标的键名 |
   | `set` 目标行首尾原样 | `值之前的部分 + 新值 + 值之后的部分` 必须逐字节出现在结果里 |

   「目标之外的字节逐字节保留」是这几条里最强的一条：它把附带损伤的定义直接落到
   字节上。只有它挡得住**同名字段**——根级 `port` 与 `server.port` 共用叶子名，
   按「改动的行提到 `port`」判断的话，改错那一个也会通过；它同时覆盖两行交换顺序、
   换行符被改写这两类行多重集看不出的改动。计划里含 `insert` 时不走这条（插入点
   在原文里不存在，`value_span_for_path` 定位不到区间），退回下面几条行级口径。

   最后一条是行级精度的来源：它保证目标行的缩进、行尾注释与 `#@` 元数据都不能被动。
   单条编辑的任务不走这套规则，沿用上面的前后缀/键集合口径，所以历史任务的语义与数字不变。

   **跨 `@include` 的任务**（`expect.target_file` 非空）用另一条路径：策略从入口文件
   出发，允许顺着 include 走到别的文件；判定拿**目标文件**的内容做上面那套比对，
   并且要求策略改动的**正是这个文件**——改到别的文件上属于定位错误，直接记误改。

   语料把文件树以内存形式交给策略（不读磁盘），策略因此仍是纯函数：同一输入必得同一输出。
3. **拒绝**：必须给出**期望的稳定错误码**。拒绝理由不对不算通过。
   否则"一律拒绝"也能在拒绝类任务上拿满分。

于是每个任务落进六种结果之一：

| 结果 | 含义 |
| --- | --- |
| 正确 | 值改对了，且改动区间之外字节零变化 |
| 附带损伤 | 值改对了，但区间之外也变了（格式、键序、空白、换行） |
| 误改 | 值不对 / 目标不对 / 结果无法解析 |
| 正确拒绝 | 该拒的拒了，且错误码正确 |
| 误拒 | 该改的拒了 |
| 该拒未拒 | 该拒的改了 |

指标口径：

| 指标 | 分母 |
| --- | --- |
| 正确率 | 应当改动的任务数 |
| 附带损伤率 | 应当改动的任务数 |
| 误改率 | 全部任务数（含"该拒未拒"） |
| 拒绝准确率 | 应当拒绝的任务数 |
| 确定性 | 同一任务重复运行、以及把任务顺序倒过来跑，结果都必须逐字节一致 |
| 注释保留 | 原文的 `#` 注释片段是否全部出现在结果里 |

## 三、三个策略

| 策略 | 定位 | 写回方式 | 写入前校验 |
| --- | --- | --- | --- |
| `verseconf-intent` | 意图契约的路径解析 | 只替换 / 插入 / 删除目标所在的字节区间 | schema + 安全双重校验 |
| `whole-file-rewrite` | 同上 | 改完之后把**整个文件**按 AI 友好规范形式重新序列化 | 无（`set`）；`insert`/`delete` 复用核心定位后整份重写 |
| `line-diff` | 按字段名找**第一处**匹配行 | 整行替换 / 末尾追加 / 删掉第一处匹配行 | 无 |

两个基线也实现 `insert` / `delete` 与**多条编辑**：只实现 `set`、或只实现单条编辑，
会让它们在新任务上直接误拒，那样比出来的就不是"写回方式的代价"，而是"谁实现了这个功能"。
`line-diff` 对多条编辑是逐条顺序作用——每条都"按字段名找第一处"，作用域信息完全缺失，
错位会叠加。

前两个的**定位方式相同**，这是刻意的：两者数字上的差异只可能来自"重写整个文件"这一步，
而不是定位能力。第三个则同时暴露定位与安全两方面的差距。

`whole-file-rewrite` 是"模型重写整个文件"的**确定性替身**。真实的模型重写通常还会丢注释，
而这里的替身用的是本仓库自己的保注释格式化器，所以它测到的附带损伤是**下界**。

## 四、当前结果

语料指纹：`162777399290a695`（8 篇文档 / 27 个任务，口径版本 `1.2`）

| 策略 | 正确率 | 附带损伤率 | 误改率 | 拒绝准确率 | 确定性 | 注释保留 |
| --- | --- | --- | --- | --- | --- | --- |
| `verseconf-intent` | 21/21 (100%) | 0/21 (0%) | 0/27 (0%) | 6/6 (100%) | 是 | 21/21 |
| `whole-file-rewrite` | 0/21 (0%) | 21/21 (100%) | 3/27 (11.1%) | 3/6 (50%) | 是 | 19/21 (90.5%) |
| `line-diff` | 6/21 (28.6%) | 6/21 (28.6%) | 10/27 (37.0%) | 2/6 (33.3%) | 是 | 8/21 (38.1%) |

口径版本从 `1.0` 升到 `1.1` 的原因是多条编辑与 `insert` / `delete` 开始纳入附带损伤判定，
并加入了键集合与行多重集的比对。`1.1` 升到 `1.2` 是因为多条编辑多了一条更强的检查
「目标之外的字节逐字节保留且顺序不变」：同名字段（根级 `port` 与 `server.port`）改错、
两行交换顺序、换行符被改写，都只有这一条抓得住。按 `1.2` 重算后三个策略的数字与 `1.1`
完全一致，说明既有 27 个任务里没有踩到这个漏洞——它补的是判定器的能力，不是历史数字。
指纹把 `tasks.json` 整体算进去，其中包含口径版本，所以这次从 `1cdd2b08db2c1132` 变成
`162777399290a695`；文档语料本身一个字节都没改。

几个具体的观察：

- **重写整个文件**：21 个应当改动的任务里，目标值全部改对了，但**没有一个**做到改动之外字节零变化；
  其中 CRLF 语料被整份改成了 LF（`CRLF 是→否`）。它还照单执行了三条本该被拒绝的改动
  （过期前置条件、破坏 schema、关闭证书校验），拒绝准确率 50%。
  注释保留 19/21 而不是满分，是因为它在删除里连同行尾元数据一起重排掉了。
- **直接生成差异**：改对 6/21。它的失败方式很有代表性——
  - **作用域**：往嵌套表里插键时它把键追加到了**文件末尾**，于是 `server.workers` 在结果里
    根本不存在（`insert-nested-key` 判为误改）；
  - **定位**：删除 `servers[name="replica"].weight` 时它按字段名找**第一处** `weight`，
    删掉的是第一个 `[[servers]]` 元素上的那个，目标仍然存在（`delete-named-list-field` 判为误改）；
  - **多条编辑**：三条多编辑任务它全部落到附带损伤或误改——
    整行替换把目标行的行尾注释与 `#@` 元数据一起吃掉了
    （`multi-set-two-tables` 期望行 `  port = 9090 #@ range(...)` 不再存在），
    也会把 `port=8080` 这种紧凑写法规范化成 `port = 9090` 而改动了目标行本身的空白
    （`multi-set-and-delete`），以及因为缺作用域而在同名元素上错位
    （`multi-set-same-named-element` 判为误改）。
  - 反过来，**根表上的单条插入与删除它做得对**——朴素做法在"不需要作用域信息、
    也不需要保留行内细节"时是够用的。这正是把这些任务加进语料的价值：
    它把"朴素实现什么时候够用、什么时候不够用"变成了可指名的数字，
    而不是一句笼统的"不够好"。
- **跨 `@include` 编辑**（4 个任务）把"朴素实现不跟随 include"这件事也变成了数字：
  `line-diff` 在 4 个任务里 **3 个直接误拒**（目标在被包含文件里，它只在入口文件里找），
  剩下 1 个（目标恰好就在入口文件里）虽然改对了值，却因为整行替换丢掉了行尾 `#@` 元数据而记附带损伤。
  `whole-file-rewrite` 定位正确但 4 个全部附带损伤（它重写整个被改文件）。
  `verseconf-intent` 4/4 正确：只改目标文件的字节区间，入口文件与其它被包含文件一个字节不动。
- **意图执行**：21/21 正确、0 附带损伤、6/6 拒绝码正确、结果确定。

> 这些数字由 `benchmark/results/latest.md` 生成。语料或判定口径变化时，指纹与数字都会变；
> 对不上时先比对指纹。

## 五、加入你自己的方案

实现一个策略只需要把「源码 + 编辑计划」映射成「新源码」或「拒绝」：

```rust
use verseconf_bench::strategies::{EditStrategy, StrategyOutcome};

struct MyStrategy;

impl EditStrategy for MyStrategy {
    fn name(&self) -> &'static str { "my-strategy" }
    fn summary(&self) -> &'static str { "一句话说明它怎么改" }

    fn apply(&self, source: &str, plan_json: &str) -> StrategyOutcome {
        // 返回 StrategyOutcome::Applied(新源码) 或 StrategyOutcome::Refused { code, message }
        # unimplemented!()
    }
}
```

把它加进 `strategies::all()` 即可；判定、指标与报告都会自动带上它，
不需要改判定脚本。这是「结果与实现解耦」的具体含义。

## 六、范围与限制

诚实起见，这些是这份基准**没有**覆盖的：

1. **跨 `@include` 的编辑已纳入**（`expect.target_file`），语料里是一层 include；
   更深的嵌套链与"目标位于被多层 include 合并出来的表里"尚未覆盖。
2. **不含真实模型**。两个基线都是确定性替身，测的是"重写/打补丁这类写法的固有代价"，
   不是某个具体模型的得分。真实模型的数字只会更差（会丢注释、会改错更多）。
3. **正确率的分母是 14 个应当改动的任务**（总计 20 个），规模仍然不大。
   语料是公开可扩展的，欢迎补任务；补完之后请一并更新指纹说明。
4. **注释保留是近似指标**：用"每行第一个 `#`"切片段，字符串值里含 `#` 会被算进来。
   精确的字节级保真由附带损伤那一项负责。
5. **判定与被测实现共享「值在哪」的定义**（`value_span_for_path`）。
   这是契约的一部分而不是实现细节，但如果契约本身把区间定义错了，
   判定会跟着错。判定方读取实际值的部分是独立的 AST 遍历，不共享实现代码。
